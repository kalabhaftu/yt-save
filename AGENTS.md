# Repository guidance

- Treat the root `prompt.txt` as the user's local master brief. Preserve it, keep it ignored, and never commit or publish it.
- This is a native Rust application for Windows 10/11. Keep Slint UI work on its event loop, run blocking or asynchronous work away from that thread with Tokio, and persist durable state in SQLite. Preserve the current `crates/yt-save` module boundaries unless a clear need justifies splitting them.
- Keep product, executable, publisher, and installer identity centralized in `branding.json`. Preserve the requested transparent icon background through asset conversion and packaging; keep app and installer names consistent.
- Accept supported media URLs from any site yt-dlp can extract. Do not add a YouTube-only host allowlist or claim universal site support; let yt-dlp analysis determine whether a URL works and report failures plainly.
- For full YouTube support, package a verified, compatible Deno runtime and pass yt-dlp its explicit path. The official yt-dlp Windows standalone executable already bundles `yt-dlp-ejs`; do not assume that this removes the JavaScript-runtime requirement. If the yt-dlp distribution changes, verify and package the matching EJS component explicitly.
- Authentication must be explicit and HTTPS-only. Use the compact, temporary WebView2 sign-in flow; never extract cookies from another browser profile or read the whole WebView cookie store. Persist only URL-matching cookies encrypted with the current Windows user's DPAPI key, pass yt-dlp a short-lived Netscape jar by path, refresh the encrypted vault when yt-dlp exits, and remove the plaintext staging file on every exit path. Never put cookie values in SQLite, diagnostics, logs, or ordinary backups. Keep the embedded sign-in and redirect limitations clear.
- Manage yt-dlp, Deno, FFmpeg, and FFprobe through the dependency manifest. Use trusted upstream sources, pinned versions, SHA-256 verification, architecture and license records, and documented update procedures. Review FFmpeg build licensing and ship applicable notices. Do not fetch unverified binaries at runtime or commit large binaries without a documented reason.
- A visible control or feature must have real behavior behind it. Do not ship fake progress, placeholder media presented as real, or nonfunctional controls. Keep the feature matrix honest about implementation, verification, and limitations.
- Add meaningful automated coverage for implemented behavior. Report only checks actually run and distinguish compile-time or fixture checks from Windows runtime, download, and installer verification. Never claim a feature or package is verified without evidence.
- Preserve user downloads, partial media, databases, and application data. Before removing build output, resolve and inspect the exact target path and contents; clean only confirmed-unused generated artifacts. Do not broadly delete `target/`, `dist/`, dependency caches, or package outputs that may be in use or contain deliverables.
