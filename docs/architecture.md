# Architecture and framework decision

## Product identity

The temporary product identity is centralized as **Yt Save**. The Rust package/executable is `yt-save`, the Windows application folder is `Yt Save`, the application data folder is selected through the `directories` crate, and the installer sources carry the same name and version. Branding is intentionally kept out of dependency and queue logic.

## UI framework

The app uses Slint with Rust. Slint supplies a declarative, native desktop UI without an embedded browser runtime and provides Windows desktop support. Its Rust components are created and accessed on the main event-loop thread. Long-running work is kept outside that thread and posted back with `slint::invoke_from_event_loop`.

The selected Slint 1.18 release requires Rust 1.92 or newer. The workspace declares that minimum and pins the stable channel through `rust-toolchain.toml`.

The project selects Slint's GPL-3.0-or-later open-source license and therefore licenses the application code GPL-3.0-or-later. A later switch to a commercial Slint license would require a deliberate licensing review and repository update.

## Runtime boundaries

- **UI:** Slint components and view models only; no process implementation inside `.slint` files.
- **Async work:** Tokio multi-thread runtime for URL analysis, SQLite I/O, queue work, and child process output.
- **Download engine:** the official `yt-dlp.exe`, invoked with structured arguments and no shell.
- **Site authentication:** a Windows-only Wry child WebView runs in a private profile. The user explicitly exports cookies only for the entered HTTPS URL; `cookie_auth` encrypts the Netscape jar with user-scoped DPAPI, and yt-dlp receives a disposable file path for inspection and download processes. Active lease paths remain tracked until refresh/cleanup finishes, preventing the periodic stale-file sweep from racing cookie refresh. Startup and 60-second cleanup sweeps check the owning process ID before deleting stale leases and retain files while a matching yt-dlp child is active. Cookies never enter SQLite or ordinary diagnostics.
- **yt-dlp engine updates:** a user-triggered stable-release updater verifies GitHub's published SHA-256 asset digest, probes the staged executable's version, and activates a per-user versioned executable through a rollback-capable marker. A Windows named mutex keeps one app instance active because its engine overlays and SQLite queue are shared per user. A shared async read/write gate coordinates yt-dlp processes with updates, while the dispatcher gate prevents a queue start from racing activation. The updater does not currently verify the upstream detached OpenPGP checksum signature and fails closed when GitHub does not provide an SHA-256 asset digest.
- **Application updates:** a separate user-triggered flow checks the branded GitHub repository using strict SemVer tags and a persisted Stable/Preview channel. Stable requires a stable SemVer tag and GitHub's stable-release flag; Preview also accepts GitHub-marked prereleases that use plain SemVer tags. It requires the published installer assets and SHA-256 digests, downloads to a bounded per-user cache, detects the installer and Inno scope from current-user HKCU or machine HKLM markers, and re-verifies the staged installer before and after transferring control to a helper. The helper waits for the app process or a cancellation signal, runs the matching interactive installer (passing `/CURRENTUSER` for current-user Inno installs), then relaunches Yt Save while respecting the single-instance mutex. Installer detection rejects missing, malformed, duplicated, and conflicting markers. The cross-installer guards see only the current user's HKCU and machine HKLM, so a machine install cannot discover Inno installations registered in other accounts' HKCU. The app refuses handoff while work is active and persists queued work as paused first. A committed-shutdown signal lets the queue dispatcher distinguish a real exit from a rolled-back handoff. The GitHub asset digest is transported through the authenticated HTTPS API; this is not an independent publisher signature, and Windows upgrade/data-retention acceptance is pending.
- **YouTube JavaScript:** Deno is an explicitly located, pinned runtime when available. The official yt-dlp executable bundles `yt-dlp-ejs`; yt-dlp can still process other supported sites without Deno.
- **Media processing:** bundled FFmpeg and FFprobe are passed to yt-dlp through `--ffmpeg-location`.
- **Persistence:** SQLite with WAL mode for durable queue state and settings.
- **History export:** a snapshot of SQLite download records is encoded as UTF-8 RFC 4180 CSV; the Windows Save dialog and file write run on blocking workers outside the Slint event loop.
- **History search:** the event task retains the latest SQLite snapshot and filters its row views locally as the query changes; queue positions are computed before filtering so they continue to reflect actual execution order.
- **Queue scheduling:** each new item receives a durable rank; High priority items sort ahead of Normal items, and rank orders work within each priority. Playlist selections are inserted in one transaction. A single Tokio dispatcher reads, registers, and transactionally claims each next row before launching it, then fills available slots up to the persisted 1–8 worker limit. Lowering the limit leaves active jobs running and delays new launches until a slot is available. Each new yt-dlp job reads the saved 1–8 HLS/DASH fragment count and passes it as `--concurrent-fragments`. Failures classified as temporary network, HTTP 408/429/5xx, or rate-limit errors can be retried up to the saved 0–5 count; retry attempts and deadlines are in SQLite. The dispatcher waits until a retry deadline without holding a worker slot, and exponential delays start at 15 seconds and cap at four minutes. Permanent extraction, access, and dependency failures stay Failed for manual action.
- **Output location:** a user-selected default folder is stored in `app_settings`; every queued item stores its own resolved folder so a later preference change cannot redirect queued, paused, interrupted, or retried work. Playlist-title subfolders are created inside that per-job destination.
- **New download presets:** mode, video quality, audio format, and audio bitrate are stored as typed string values in `app_settings`, independently from each job's persisted selections. The app loads them at startup and updates them only after a new queue insertion succeeds; retry, resume, and recovery paths do not write these defaults.
- **Clipboard URL review and tray:** Windows clipboard monitoring is off by default and starts only after an explicit user choice. A dedicated message-loop thread forwards only a locally parsed, single HTTP(S) URL with the foreground monitor's work area and Windows notification state; raw clipboard text is not stored. When notifications are allowed, a Slint popup appears above the taskbar work area without taking keyboard focus. It expires after 12 seconds, and metadata lookup or queueing begins only after an explicit button click. Add-to-queue inspects playlist state first and presents playlist entry selection. The Slint system tray menu exposes window, queue, download-folder, and orderly-quit actions; close-to-tray and minimize-to-tray preferences are off by default and persisted in SQLite. Windows runtime acceptance remains pending.
- **Windows packaging:** WiX Toolset 5.0.2 for MSI and Inno Setup 6 for EXE installers.

## Rust module layout

The app crate keeps one shared `app` state boundary, with focused child modules for independent Windows workflows. `app.rs` owns Slint startup and cross-feature wiring; `app/tray.rs` owns tray actions and orderly shutdown; `app/cookie_login.rs` owns the compact WebView2 sign-in flow and its URL-scoped cookie handoff. Keep those modules narrow: UI components stay on the Slint event loop, and process, database, and network work stays on Tokio or blocking workers.

`persistence.rs` owns SQLite opening, migrations, the shared `Store` type, and row conversion helpers. `persistence/downloads.rs`, `persistence/settings.rs`, and `persistence/subscriptions.rs` implement the `Store` operations for their respective domains. Persistence tests live under `persistence/tests/`, grouped by those same responsibilities. This keeps the public store API stable while making schema, download state, settings, and subscription logic reviewable in smaller files.

## First vertical slice

The implemented flow accepts any HTTP(S) URL, obtains metadata with yt-dlp JSON output, runs a download, parses machine-readable progress, and stores completion or failure. The app does not maintain a site allowlist. yt-dlp decides whether a URL has a usable extractor. Download destinations are checked as existing directories and canonicalized before a queue item is persisted. Queue actions inspect playlist URLs before persistence so users can select entries rather than accidentally queueing a whole playlist.

Pause, resume, retry, cancel, playlist item selection, tray controls, and crash recovery have persisted implementations. They still need the Windows runtime acceptance checks listed in the feature matrix; the clipboard popup also awaits focus and monitor-placement validation there.

Queue order and priority are persisted separately from creation timestamps. The dispatcher is the only component that starts queued downloads; reorder and claim operations serialize through SQLite, and active downloads finish or pause before the next pending item is selected.
